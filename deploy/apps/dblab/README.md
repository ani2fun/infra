# dblab

A disposable polyglot database lab: six database engines plus a messaging layer, for learning on
and for evaluating [Bytebase](../bytebase/README.md) as a client. Everything here holds obviously
fake seed data and is safe to destroy at any moment.

> Connection strings, port-forwards, native-client recipes and troubleshooting are in
> [../bytebase/OPERATIONS.md](../bytebase/OPERATIONS.md).

## Deliberately NOT Argo-managed

Argo CD's `selfHeal` + `prune` would recreate this namespace the instant `lab-nuke.sh` deleted
it, which defeats the entire point of a disposable lab. It is applied by hand through the
scripts below — the same way `keycloak` is.

## Lifecycle

```bash
deploy/apps/dblab/scripts/lab-up.sh       # create + wait + seed. Idempotent.
deploy/apps/dblab/scripts/lab-verify.sh   # pass/fail table, non-zero exit on failure
deploy/apps/dblab/scripts/lab-stop.sh     # scale to 0 — frees ~4 GiB, keeps all data
deploy/apps/dblab/scripts/lab-nuke.sh     # delete namespace + PVCs + data. Asks first.
```

Use **stop** when you want the RAM back but expect the same data later — restart is seconds and
needs no re-seeding. Use **nuke** when you want the disk back or a guaranteed-clean slate;
rebuilding takes a few minutes, almost all of it Cassandra.

### It stops itself after 4 hours

`lab-up.sh` writes an absolute deadline into a `dblab-lifecycle` ConfigMap, and the
`dblab-autostop` CronJob (every 15 min) scales everything to zero once that passes. Forgetting to
run `lab-stop.sh` is the normal case, and the lab costs ~3.8 GiB of wk-1 whether or not anyone is
using it.

An **absolute** deadline rather than pod uptime means a restart or reschedule cannot silently
extend the session; epoch seconds mean the CronJob's UTC schedule and your local timezone can
never disagree.

```bash
LAB_TTL_HOURS=8 deploy/apps/dblab/scripts/lab-up.sh   # longer session
kubectl -n dblab delete configmap dblab-lifecycle     # disable auto-stop for this session
kubectl -n dblab get configmap dblab-lifecycle -o jsonpath='{.data.shutdown-after}'  # when?
```

No ConfigMap means no deadline and the job does nothing — so a lab brought up by hand with
`kubectl apply -k` is never stopped by surprise. Only PVC-preserving scale-to-zero is ever
automated; nothing deletes data on a timer.

## What runs

| Service | Image | Port | Notes |
|---|---|---|---|
| PostgreSQL | `postgres:17` | 5432 | 3 related tables with real foreign keys |
| MongoDB | `mongo:8` | 27017 | nested documents + array fields |
| Redis | `redis:8-alpine` | 6379 | mixed types: string/hash/list/set/zset/TTL; `--databases 2` |
| Elasticsearch | `elasticsearch:8.19.19` | 9200 | security **off**; explicit (non-dynamic) mapping |
| Cassandra | `cassandra:5` | 9042 | `PasswordAuthenticator` on; compound primary key |
| DynamoDB Local | `amazon/dynamodb-local:3.3.1` | 8000 | `-sharedDb`; partition + sort key |
| Kafka | `apache/kafka:4.3.1` | 9092 | KRaft, no ZooKeeper |
| Kafbat UI | `ghcr.io/kafbat/kafka-ui:v1.0.0` | 8080 | ClusterIP only — port-forward to reach it |
| RabbitMQ | `rabbitmq:4-management` | 5672 / 15672 | management plugin built in |

Kafka and RabbitMQ are **not** managed by Bytebase — they are not databases, and the NetworkPolicy
does not admit Bytebase to their ports.

Nothing here is exposed through Traefik. Everything is ClusterIP-only, reached from Bytebase or
via `kubectl port-forward`.

## Layout

| Path | What |
|---|---|
| `base/` | one file per engine (PVC + Deployment + Service), plus namespace and NetworkPolicy |
| `seed/files/` | the seed scripts themselves — real files, lintable and diffable |
| `seed/jobs.yaml` | one idempotent Job per engine; each waits on its engine's own client |
| `scripts/` | the four lifecycle scripts |

Credentials are **generated by `lab-up.sh`** into a `dblab-credentials` Secret and never
committed — so a nuke really does leave nothing behind. Read them back with:

```bash
kubectl -n dblab get secret dblab-credentials -o jsonpath='{.data.postgres-password}' | base64 -d
```

## Two traps worth knowing

Both were hit while building this and are commented in the manifests:

- **Every exec probe needs an explicit `timeoutSeconds`.** It defaults to **1 second**, and
  `cqlsh`, `mongosh` and the `kafka-*.sh` helpers are all far too slow to start in that time —
  the container restart-loops while its log insists the server started fine.
- **Kafka needs `publishNotReadyAddresses: true`.** It advertises its Service DNS name, but a
  Service has no endpoints until the pod is ready, so the readiness probe can never pass.
